# 本地处理与视觉请求可靠性优化验证

日期：2026-10-23。仅修改独立调试服务，不改变摄像头生产链路。首次导入的历史验证仍见 [verification.md](verification.md)。

## 实测范围

同一份获准本地处理的 184.85 秒、2560×1440 HEVC 素材，沿用已保存的决定，输出 30 秒 / 3 段精选和 1 个 3 秒表情包。全程零 AI 调用；没有覆盖历史任务、决策或成片，素材与结果只保存在被 Git 忽略的本机目录。

旧 / 新实现串行运行于同一台 Windows / i7-1260P（12 核、16 逻辑处理器）电脑，使用同一服务虚拟环境与 FFmpeg 8.1.2。没有并行运行其他基准编码器，但未控制操作系统背景负载、缓存或温度；下面是这次实测，不是所有视频固定快一倍的承诺。

| 实际工作 | 旧实现（秒） | 最终实现（秒） |
| --- | ---: | ---: |
| 源片元信息、完整帧索引与摘要 | 56.563 | 12.625 |
| 精选编码与全部内部校验 | 90.718 | 70.484 |
| 表情包 MP4、GIF 与全部内部校验 | 53.344 | 16.391 |
| **以上合计** | **200.625** | **99.500** |

本次合计减少 **50.4%**。这不是网页整轮生成耗时：**不含抽取采样图片、拼图、AI、圈选、排队等**。更早的 309 秒历史本地记录负载和统计范围不同，不作为本次对照基线。

复现工具是 [benchmark_media.py](../scripts/benchmark_media.py)，需要自己持有完整的源片及对应保存记录，并分别指定实现目录、只读来源任务和新的输出根目录；不要并行运行两个编码基准。`--fingerprint` 在计时结束后额外比较解码结果，不混入上表。

## 提速与保真证据

1. 输出 MP4 的真实帧数和时间戳由一次完整帧扫描共同获得，取消原先额外的计帧解码；严格完整音视频解码仍保留。
2. 表情包 MP4 / GIF 从同一次源解码的两个像素分支编码；GIF 不从有损 MP4 二次取材。主片仍使用原来的 `libx264 / fast / CRF20 / 无B帧`，不缩画幅、不强制固定帧率、不改变编码线程。
3. 仅 ffprobe 完整帧扫描默认指定 4 个输入解码线程。专门近邻对照：自动线程 45.703 秒，4 线程再次扫描 12.484 秒。3685 帧的 `best_effort_timestamp`、`best_effort_timestamp_time`、`duration`、`duration_time` 全部逐项一致；原始 JSON 的差异是附带 SEI 信息的数量，不是时间轴差异。
4. 最终旧 / 新精选 MP4、表情包 MP4 和 GIF 的逐帧解码指纹完全一致；两个 MP4 的解码音频摘要也完全一致。宽高、真实帧数、PTS、音轨、色阶及严格完整解码检查全部通过。
5. 合成媒体还覆盖 H.264 / HEVC、VFR、无音轨、音频时间缺口、旋转及全范围色阶；表情包 GIF 与原先直接读取原片的参考方案逐字节一致。

`MUKBANG_FFPROBE_THREADS` 接受 0–32 的整数，默认 4，0 恢复自动；不同机器应按自己的素材实测，而不是将这个笔记本结果推广为通用最优值。

## 两种失败的处理

- 系统技术提示要求使用采样的实际小数时间，全部精选引用帧须位于批准的半开上下文范围内。越界错误列出帧号、实际时间、允许范围与偏差。没有放宽容差、偷偷扩上下文或更改用户已发布的审美全文；AI 仍可能违反要求，此时明确失败并保留证据，不宣称从此不会选错。
- AI 等待默认从 240 秒改为 600 秒，`MUKBANG_VISION_TIMEOUT_SECONDS` 允许 30–1800 秒。连接、响应头及完整 JSON / SSE 正文共用一个可取消的绝对截止时间；不能靠不断收到少量内容延长等待。超时关闭在途连接、保留已收到的脱敏原文，不遗留后台请求线程，不自动重试。关闭本机连接不等于远端一定停止计费。

## 耗时口径与兼容

源片索引、输出编码、元信息检查、单次帧数 / PTS 扫描、严格完整解码及 GIF 检查分别记录为父阶段下的 `details`。这些已经包含在父耗时中，网页缩进展示，不重复计总和。旧任务没有内部计时，不补造历史数字；失败和取消保留已执行的部分。

公共耗时结构仍为 `schema_version:1`，新增可选字段。同步 worker、HTTP 接口、反馈缓存、已发布 Prompt 和离线恢复继续兼容。测试默认封锁真实同步 / 异步 HTTPX transport，必须明确注入模拟响应。
