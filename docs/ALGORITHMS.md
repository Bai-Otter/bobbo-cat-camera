# 进食识别与吃播是怎么做的？

[返回首页](../README.md) · [手机与服务器各做什么](ARCHITECTURE.md) · [开发者技术参考](ALGORITHM_REFERENCE.md)

BOBBO 不只是“画面里出现猫就记一次吃饭”。它要分别回答：有没有猫、是不是在吃饭、算哪一顿，以及哪些镜头值得留下。

下面围绕这些功能解释。具体参数和函数留在技术参考里，方便需要开发的人继续查。

## 一、怎样从长录像里找到猫？

不必对一段空画面反复做复杂判断。程序可以先隔一段时间查看画面，找出可能有猫的部分，再把注意力放到这些时间附近。

找到猫的某个瞬间后，还会把前后的一段时间考虑进去，避免只留下一个点，漏掉猫走近饭盆或短暂转头的过程。

这就是“粗筛”的意思：先圈出值得仔细看的范围。它只说明可能有猫，并不说明猫已经在吃饭。

代码里保留了不同分析版本，具体采用哪种筛查方式，要看运行设置；不能理解成所有版本都固定“先剪出一小段，再分析一遍”。

相关代码：[视频检查](../vision/src/video.py)、[找猫](../vision/src/detectors.py)、[安排分析任务](../server/src/feedAnalysis/coordinator.js)。

## 二、怎么判断猫是在吃饭，而不是路过？

进一步分析时，程序会结合几个线索：

- 饭盆在画面的什么位置？
- 猫脸、嘴鼻是否靠近饭盆？
- 头部朝向和附近动作是否符合碗边进食的情况？
- 这种情况持续了一段时间，还是只出现了一瞬间？

因此，路过镜头、站在旁边和靠近饭盆，需要区别对待。单独一次移动警报不足以证明正在进食。

保留的 V3.2 版本也会检查猫脸、姿态和嘴鼻附近的动作。不过，当前最终统计主要依据脸部在碗边接触的证据，并不是每一秒都数清楚了咀嚼动作。因此它给出的是进食行为估计，不能用来计算精确食量或咀嚼次数。

相关代码：[V3.2 进食判断](../vision-v32/src/feeding_behavior.py)、[整理进食记录](../server/src/feedAnalysis/feedingStats.js)。

## 三、怎么整理成“吃了几顿、吃了多久”？

猫咪吃饭时可能抬头、停一下，又继续吃。如果每次短暂停顿都算新的一顿，记录就会非常零碎。

程序会先整理各个时间段的状态，再结合前后画面处理短暂缺失，把属于同一次进食的部分归在一起。

要注意两个时间不一样：

- **这一顿从什么时候到什么时候**：包含中间可能存在的停顿。
- **计入进食的时长**：按判断规则累计，不是把整段停顿也全部算进去。

如果某段画面没有成功分析，也不能直接当作“这段时间没有猫”。

回放里的颜色同样应该表示有开始和结束的区间：绿色表示有猫，橙色表示进食。它们不是只标一次开始时间，也不能因为一个瞬间看到猫，就把整段录像都涂绿。显示时还要与原录像的时间对齐。

相关代码：[进食时长、餐次和时间段](../server/src/feedAnalysis/feedingStats.js)。

## 四、开始进食提醒为什么要单独判断？

移动警报的意思只是“画面发生了变化”。人走过、光线变化等也可能触发，所以不能把每次警报都作为进食提醒发出去。

开始进食提醒需要先看到持续的进食迹象，并检查是不是刚发生的事情，还要避免同一顿反复通知。

这里尤其要区分：**整理历史记录，不等于报告正在发生的事情。** 历史录像末尾也可能有猫吃饭，所以部署时必须检查录像实际发生的时间，不能只凭“分析发现进食”就立即通知。

相关代码：[开始进食确认](../server/src/feedAnalysis/feedingStartConfirmation.js)、[任务安排与提醒协调](../server/src/feedAnalysis/coordinator.js)。

## 五、一键吃播怎样挑出贴脸镜头？

它不是随机截取，也不是单纯选择“有猫”的画面，而是更偏向这些镜头：

- 猫脸在画面里比较大，能看清表情。
- 朝向镜头或角度合适，不是一直背对镜头。
- 脸部比较完整，没有被严重挡住。
- 前后动作连贯，能组成一段自然的视频。

程序先给这些线索打分，找到比较好的瞬间，再向前后保留一小段动作。这样留下的是一段可看的镜头，而不是一张好看的画面一闪而过。

相邻、重复的候选会合并或去重，过长的部分会拆分。默认倾向每段约 6 秒，通常在 4–8 秒之间；具体设置可以调整。

这里的分数只是挑镜头的依据，不是猫咪健康评分，也不代表所有人都会觉得同一段最可爱。

相关代码：[判断猫脸和镜头特点](../vision/src/cute_highlights.py)、[选出连贯片段](../vision/evaluation/cute_segments.py)。

## 六、怎样把一天的几顿饭做成一个精选？

程序汇总当天已经准备好的进食素材，先让不同素材里的好镜头有机会入选，再补充其他质量较好的镜头，去掉重复，按时间顺序剪到一起并配乐。

这不是“每顿各做一条精选”，而是从一天的多顿素材里整理当天的精选。时长有限时，不保证每顿都能被选进去。

成片时长偏好包括：

| 选择 | 含义 |
| --- | --- |
| 自动 | 根据可用餐次数安排长度，素材少就短一些 |
| 精简 | 最多 30 秒 |
| 标准 | 最多 60 秒 |
| 丰富 | 最多 120 秒 |

这些是长度上限，不是必须凑满的秒数。没有足够好镜头时，不会为了凑长而反复使用同一段。

背景音乐需要部署者准备有使用授权的文件；公开仓库没有附带音乐，未配置音乐时，每日精选可能无法生成。

相关代码：[汇总全天素材](../server/src/foodcast/automationService.js)、[剪辑和配乐](../server/src/foodcast/renderer.js)、[音乐管理](../server/src/foodcast/bgmLibrary.js)。

## 七、之前用来给视频打标签的网页在哪里？

在 [视频标记工具](../vision/annotation/README.md)。

可以导入本地视频，把“这段可爱、应该保留”和“这段不合适、应该排除”标出来，再导出标记结果。它帮助开发者对照人的选择，检查自动精选是否选得合理。

打完标签不代表系统就会自动学会新偏好；还需要用这些结果做比较、测试和调整。
